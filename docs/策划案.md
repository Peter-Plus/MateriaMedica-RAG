# 基于 RAG 的中药信息问答系统：策划案

## 1. 项目定位

面向生物信息学课程的五人小组作品。用户通过 Windows 客户端查询《本草綱目》中的药材信息。系统先检索古籍片段，再由大语言模型用现代中文整理回答，同时展示片段所在文档、章节、条目及原文行号。目标是稳定完成端到端演示，并留下添加资料、替换模型和开展评测的扩展点。

## 2. 初版范围

| 模块 | 初版功能 |
| --- | --- |
| 账号 | 用户名和密码即时注册、登录、退出；无验证码 |
| 对话 | 提问、查看按账号保存的历史对话 |
| 知识库 | 导入 UTF-8 `.txt`，按章节和药材条目切分，支持重新导入更新 |
| 检索 | 简繁归一化关键词检索，可补充 embedding 向量检索 |
| 生成 | 调用服务端配置的低成本云模型，要求依原文作答 |
| 引用 | 展示对应古籍片段、章节、条目和原文行号 |
| 部署 | 本地运行；域名和访问方式确定后部署至现有 Ubuntu 服务器 |

不把古籍内容作为现代疗效的证据，不提供针对个人的诊断、处方或剂量建议。资料不足时明确说明，避免凭模型常识补写“古籍原文”。

## 3. 用户流程

1. 打开 Electron 客户端，设置本地或 HTTPS 服务端地址。
2. 即时注册或登录。
3. 输入“甘草在《本草綱目》中有哪些记载？”等中文问题。
4. 服务端检索相关原文，模型整理回答；客户端展示回答和可展开的出处。
5. 用户可以回到历史对话继续提问。

## 4. 技术路线

客户端使用 Electron 的主进程代理网络请求；渲染进程通过受限 preload 接口访问后端，不直接持有模型 API Key。后端使用 Python 标准库 HTTP 服务与 SQLite，降低课程项目的部署依赖。密码使用 scrypt 加盐哈希，会话 token 在服务端以哈希保存。数据表包含账号、会话、对话、消息、资料、片段。

检索采用两条路径：关键词路径在没有模型密钥时即可检查；向量路径通过兼容 OpenAI 的 embedding 接口构建。两路结果融合后最多提供五段原文给模型。生成提示词要求标注 `[1]` 等出处编号，并把检索内容仅当作资料，避免其中的指令影响回答。

## 5. 资料与更新

初始资料为用户提供、可随项目分发的《本草綱目》电子文本。初版使用整份文本。后续可以通过命令行增加多份 UTF-8 `.txt`，同名文件内容变化时替换旧索引。单文件默认不超过 20 MB；格式、操作与模型切换细节见[部署与更新](部署与更新/README.md)。

## 6. 演示与验收

- 客户端能打开并连接本地后端。
- 新用户能注册、登录；不同账号只能看到各自历史对话。
- “甘草”“人参”等简体问题能检索到繁体原文及行号。
- 配置真实 API Key 后，回答附有与内容对应的古籍出处。
- 资料更新后，检索结果反映新版本。

课程效果评估由其他组员后续补充。预留“直接问模型 vs RAG 问答”的题库与人工核查流程，初版不宣称准确率提升。

## 7. 风险和处理

| 风险 | 处理 |
| --- | --- |
| 文言文与现代提问差异 | 简繁转换、关键词与向量融合；后续根据测试题改进 |
| 古籍误用与幻觉 | 引用原文、资料不足时拒绝推断、界定医疗建议边界 |
| API 费用被滥用 | 每账号与全站每日问答上限、注册人数上限、请求速率限制 |
| 公网密码传输 | 服务端只监听本机，由 HTTPS 反向代理对外提供服务 |
| 外部 API 或网络不可用 | 清晰返回错误；知识库检索可离线检查，生成依赖云 API |

## 8. 可扩展方向

增加权威现代资料、来源版本信息、测试题库和人工评价；添加更好的古文分段、重排序、流式输出与管理员知识库页面。所有扩展在核心链路验证后进行。
