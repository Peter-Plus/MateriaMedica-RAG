# RAG 更新

当前流程为：`UTF-8 古籍 → 按章节/条目切分 → SQLite 全文索引 → 关键词检索 + 可选向量检索 → 最多 5 段原文 → 云模型回答并展示出处`。多本书共用同一个知识库，每段都带文档名、章节、条目及原文行号。**增加普通文本资料不需要重写 RAG 流程**，具体导入见[文献更新与扩展](文献更新与扩展.md)。

## 补充向量

文本导入后即可参与关键词检索；向量是可选的付费增强。服务器目前仅为初始 3360 个片段中的 1 个片段生成过向量。先小批量验证，再按预算补齐：

```bash
sudo -u bcrag bash -c 'cd /opt/bcrag && python3 -m server.ingest --embed --embed-document "伤寒论-某版本.txt" --max-embed 20'
```

`--embed-document` 使用知识库中显示的**文件名**，只补这一本文献缺失的向量；不指定时处理所有文献的待生成向量。去掉 `--max-embed 20` 会持续处理所选范围内的全部片段并产生更多 API 用量。此参数已在本地代码中实现；在服务器使用前，先按[后端更新](后端更新.md)同步新版 `server/`。

## 什么时候需要修改 RAG 代码

- **章节和条目识别不准**：新古籍排版与《本草綱目》差异较大时，先检查检索结果中的章节、标题、行号，再调整 `server/knowledge.py` 的分段规则或准备保留原文依据的规范化文本。
- **检索质量不足**：准备跨书测试题，记录应命中的书与段落，再决定是否调整关键词、向量融合或增加重排序。不要仅凭一次问答改模型参数。
- **更换向量模型或维度**：旧向量与新向量不能混用。需要备份数据库并对片段向量做迁移后重建；不要直接删除整个 SQLite 数据库，否则账号与对话也会消失。
- **资料量显著增加**：当前向量检索会线性读取已生成的向量。课程规模可以先用；较大规模需评估索引或专用向量库。

若只改了 `server/` 中的检索算法或模型提示词，按[后端更新](后端更新.md)部署并重启。若只上传并导入新文本，后端无需重启。
